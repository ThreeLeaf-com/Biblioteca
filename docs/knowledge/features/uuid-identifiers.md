# UUID Identifiers

Every entity in this package is keyed by a UUID, never by an auto-increment
integer. Some of those UUIDs are generated by the framework, and some are
**derived from the row's own content**. The difference matters, so read this
before assuming an id is opaque.

## Deterministic keys — the core of the text hierarchy

Seven models mint their key from a distinguished name rather than at random.
Each declares a `get<Entity>IdAttribute()` accessor that, when the key is still
empty, builds an X.500-style distinguished name from the row's own fields and
hashes it with `UuidUtil::generateX500Uuid()`:

| Model       | Distinguished name                                |
| ----------- | ------------------------------------------------- |
| `Author`    | `sn=<last_name>,givenName=<first_name>`           |
| `Publisher` | `cn=<name>`                                       |
| `Series`    | `cn=<title>,creator=<author_id>`                  |
| `Book`      | `cn=<title>,creator=<author_id>,o=<publisher_id>` |
| `Chapter`   | `cn=<title>,o=<book_id>,ou=<chapter_number>`      |
| `Paragraph` | `o=<chapter_id>,ou=<paragraph_number>`            |
| `Sentence`  | `o=<paragraph_id>,ou=<sentence_number>`           |

Because a UUID v5 is a hash of namespace plus name, the same content always
produces the same id, on any machine, with no coordination. Two consequences
follow, and they cut in opposite directions:

- **Re-importing the same source data is idempotent.** An importer can recompute
  an id instead of storing a mapping table.
- **The id encodes the content, and changing the content does not change the
  id.** The accessor only fills an _empty_ key, so renaming a book after it is
  saved leaves an id derived from the old title. Treat the derivation as a
  seeding rule, not an invariant.

Note also that a deterministic key means two independently created rows with
identical identifying fields collide on the primary key rather than coexisting.
For `Author` that is `(first_name, last_name)`; for `Paragraph` it is
`(chapter_id, paragraph_number)`.

## Framework-generated keys

The remaining eight entity models — `Annotation`, `Bibliography`, `Figure`,
`Genre`, `Index`, `Note`, `TableOfContents`, `Tag` — carry no such accessor and
rely on Laravel's `HasUuids` concern to supply the key on insert. (The seven
models above declare `HasUuids` as well; their accessor is what actually supplies
their key.)

**These keys are time-ordered, not random,** and exactly which flavour depends on
the framework version the host application resolves. Under Laravel 13,
`HasUuids::newUniqueId()` returns `Str::uuid7()` — a UUID v7, whose leading bits
are a millisecond timestamp. Do not rely on the specific version; do not assume
the value is unpredictable, and do not use it as a secret or an unguessable
handle.

The three pivot models — `BookTag`, `BookGenre`, `SeriesBook` — mint no key of
their own. Their primary key is the pair of UUIDs already held by the rows they
join.

## Column shape

The column is a `uuid` typed column named after the entity — `book_id`,
`chapter_id` — declared as `$table->uuid('...')->primary()` in the migration.
See [Database Schema](/data/models/database-schema.md).

**Do not order by the key.** A hashed v5 carries no time information at all, so
for the seven content-derived models the id says nothing about creation order.
The framework-generated keys happen to be time-ordered, but mixing the two
schemes across the codebase makes key order meaningless as a general rule. Order
comes from the explicit `chapter_number`, `paragraph_number`, `sentence_number`,
and `b_series_books.number` columns, and from the timestamps.

## UuidUtil

[`UuidUtil`](../../../src/Utils/UuidUtil.php) wraps
`Symfony\Component\Uid\Uuid` and exposes four deterministic v5 generators, one
per standard namespace:

| Method                     | Namespace              | Normalizes input | Validates input                                      |
| -------------------------- | ---------------------- | ---------------- | ---------------------------------------------------- |
| `generateDnsUuid(string)`  | `Uuid::NAMESPACE_DNS`  | trim, lower-case | `FILTER_VALIDATE_DOMAIN` with `FILTER_FLAG_HOSTNAME` |
| `generateUrlUuid(string)`  | `Uuid::NAMESPACE_URL`  | trim, lower-case | `FILTER_VALIDATE_URL`                                |
| `generateOidUuid(string)`  | `Uuid::NAMESPACE_OID`  | none             | `/^\d+(\.\d+)*$/`                                    |
| `generateX500Uuid(string)` | `Uuid::NAMESPACE_X500` | none             | **none**                                             |

The first three raise `InvalidArgumentException` on a malformed input.
`generateX500Uuid()` validates nothing and hashes whatever string it is given —
which is why an empty `title` or a null `publisher_id` still produces a
well-formed id, just one derived from a partly empty distinguished name.

Only `generateX500Uuid()` has callers inside `src/`. The other three are
provided for host applications that need a stable id derived from a hostname, a
URL, or an OID.

The class documents [RFC 9562](https://datatracker.ietf.org/doc/html/rfc9562)
for UUIDs and [RFC 1035](https://datatracker.ietf.org/doc/html/rfc1035) for
hostname format.

## Composite keys

`SeriesBook` keys on `['series_id', 'book_id']` and uses the
[`HasCompositeKey`](../../../src/Traits/HasCompositeKey.php) trait, because it
extends `Model` and plain Eloquent supports one key column only. `BookTag` and
`BookGenre` extend Laravel's `Pivot` base class instead, which already handles a
two-column key, so they need neither the trait nor a `$primaryKeys` property.
See [Domain Model](/data/models/domain-model.md).
